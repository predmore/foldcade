# Save safety audit

Design input, 24 November 2026. Research only; no product code, emulator settings, grants, games, or device files were changed. The attached Thor was inspected with adb 35.0.2 on port 5042, using read-only commands. No app was launched, stopped, or sent input. Azahar's running game was left alone.

## Required safety contract

**RomM is the source of truth; the emulator's files are a working copy.** A save that exists only on a device is at risk, even when the emulator is working perfectly. The useful promise is: this game's current progress has a verified off-device copy, and the emulator will read the intended working copy. A green check based on a retained folder grant cannot establish either promise.

Other save services can satisfy the off-device requirement, but the service must cover this game and have finished uploading. A Steam ID, Steam Cloud capability, or an installed cloud client does not establish that. Firmware, BIOS files, Switch keys and firmware can also come from RomM; they must not be described as inherently device-only. Settings, controller mappings, shader caches and installed graphics drivers normally cost re-setup or rebuilding if lost. Console-specific identity and account/profile data need separate care: some are more consequential than ordinary settings.

For a wrong-folder repair or emulator migration: preserve every distinct local save first, upload/verify it on RomM as a version or kept-both archive, resolve the intended head, bind the proven live destination, then place RomM's head there and verify the bytes. Do not promote an incidental fresh save above established progress merely because its timestamp is newer. If RomM is unavailable, keep all local copies and leave the repair pending; a second copy on the same Thor is temporary protection, not completion.

## What Foldcade currently proves and shows

The existing implementation already has important byte-preservation protections. This proposal should extend them.

1. `app/src/main/kotlin/app/foldcade/SaveFolderFinder.kt:10` preserves a manually chosen folder. Auto-found folders are rediscovered; `:24` uses known paths, reachable grants, loose markers and the emulator's permission on that exact candidate. `:64` requires **any** marker, not all markers. A permission is evidence of permission, not evidence of the current setting. `AndroidSaveFolderFinder.kt:27` reads Foldcade's persisted grants; `:51` checks the player's permission, without root. Android does not offer Foldcade the emulator's private preferences or a complete unprivileged list of its current folder choices.
2. `app/src/main/kotlin/app/foldcade/FoldcadeApp.kt:1661` runs discovery. `:1685` intentionally keeps a chosen folder bound based on its retained grant rather than dropping it for slow I/O. Eden's explicit per-package grant takes precedence (`:1672`). `:1707` announces newly found folders, but no adapter currently verifies ongoing live use of a manually chosen copy.
3. `app/src/main/kotlin/app/foldcade/PlayerSaves.kt:251` resolves a game's save spots from the ROM display name/header and plugin methods. `:321` hands changed hashes to the library; missing/unreadable reads can yield no observed change. `:365` places held saves and verifies them. Its protections include backing up overwritten files, refusing unacknowledged changes, read-back checks, rollback and pending/torn-write marks (`:196`, `:915`). Backups are capped at 20 **per player**, not per game (`:932`). The mark key at `:935` includes library, game, player, slot and filename, but not the folder URI or emulator install identity.
4. `app/src/main/kotlin/app/foldcade/LaunchSaves.kt:34` captures outside changes before server negotiation and placement. `:52` explicitly guards unresolved Eden/PPSSPP/Dolphin/EX destinations; known incoming saves stop those launches. `:133` passes only resolved slots to the library, so unresolved slots must not be acknowledged as placed. Byte verification still cannot prove that the emulator opens that spot. Unsupported formats and missing folders can be played by an explicit per-launch opt-out.
5. `plugins/romm/src/main/kotlin/app/foldcade/plugins/romm/RommLibrary.kt:819` durably keeps observed bytes before background upload; `:1687` copies the previous held file to trash and leaves the synced hash unchanged. `romm/src/main/kotlin/app/foldcade/romm/SaveLedger.kt:12` tracks accepted hashes, archived hashes and emulator per slot; unknown history is unsynced. `RommClient.kt:705` preserves conflicts rather than trusting clocks. These ledgers describe bytes Foldcade has observed, **not** an emulator's live root. A fresh valid save can therefore become the newest uploaded version when no divergent-server conflict exists.
6. `app/src/main/kotlin/app/foldcade/GameSaveHealth.kt:16` detects missing folder/hosted grant/setup; `:36` combines cached slot reachability with declarations. `language/src/main/kotlin/app/foldcade/language/SaveHealth.kt:17` returns `DeviceOnly` when there is no server copy or no supported sync, `NotSyncing` for setup issues, `Waiting` for held unsent progress, otherwise `Fine`. `Fine` has no warning line. **Non-emulators return `Fine` first**, without cloud verification. A missing selected player similarly often becomes `Fine` (`ShellController.kt:770`).
7. `language/src/main/kotlin/app/foldcade/language/SaveSetup.kt:109` considers a tile done when its rows have no remaining step; `:120` labels that `Syncing`. `:133` derives steps from existing rows. `:150` prioritizes emulators used by Home games. This is setup status, not independent save-location or upload evidence. `app/src/main/kotlin/app/foldcade/SaveNotices.kt:16` reports kept-both and queued outcomes; unchanged wrong-folder sessions generate neither. Waiting notices get a 45-second patience period; setup notices apply to emulators used by Home games. A reachable abandoned folder can keep the Settings check, no amber game badge, and no R1 notice indefinitely.

### Recovering an apparent loss today

RomM retains upload history. **Y › Saves** on a game with a server copy lists versions across devices, slots and emulators; selecting a save and confirming Play restores it as a new head while preserving existing progress. Implementation: `RommLibrary.kt:852` lists versions, `:875` marks kept-both archives, `:880` derives Playing from held bytes/ledger; `app/src/main/kotlin/app/foldcade/ServerSaveFlow.kt:23` captures current changes before choosing; documented at `docs/integrations/romm.md:148`.

This is a useful recovery surface, but not sufficient for a non-technical user facing the incident. Nothing currently tells them to open it when the abandoned folder matches the ledger. Playing means Foldcade's held selection, not proven emulator consumption. A restore still writes to the wrong root until binding is repaired. Some players require the ROM downloaded to resolve identity; network, firmware/restart or emulator-format compatibility may prevent an immediate restore. Device-local backup/trash copies are not all presented in this version list, and unobserved live-folder progress never reached RomM. Add a persistent “Your save is still on RomM” recovery action to folder mismatch incidents, show the verified target path, and preserve both local histories before selecting a head.

## Safest checks shared by all adapters

- Track separate facts: server head last checked/accepted; working-copy hash placed; live location confidence and its evidence time; game identity resolution; flush/session completion; unsent local copies. Display “Folder found”, “Location verified”, “Saved to RomM”, “Waiting”, and actionable faults truthfully. A setup check cannot stand for all of these. Persist incidents across restart and expose the same reason in the game tile, Settings, R1 and Y › Saves.
- Before launch, recheck read/write grant ownership, folder enumeration, resolved identity, effective emulator settings and known server/held save presence. Distinguish absent files, empty data, unreadable files and failed provider queries. If a known server save cannot be mapped/placed or a positive mismatch exists, stop the ordinary launch and offer repair/recovery plus an explicit at-risk opt-out. If the server cannot be checked, show the cached head's age; never promise that it is newest across devices.
- Save a pre-launch manifest: URI identity, selected package/version/install epoch, effective game/account/card settings, relevant file names, sizes, hashes and available mtimes. Recheck after return. A held server save alongside a missing working-copy save is an inconsistency to explain, even when the ledger's held bytes are “synced”. Tie location verification to the current binding/install, not just a per-game hash mark.
- Compare the returned game-save archive against the previous manifest/server head before promotion: missing expected members, large size reductions, blank/formatted cards, a known initial-save fingerprint, a newly created account, or a new one-file save after root migration should keep both versions and ask which progress to continue. These are **regression suspicions**, never proof of lost game progress. Equal-size saves may reset progress; a legitimate game can shrink/delete files. Format-specific structural checks are safer than universal “percentage complete” guesses. Use the existing kept-both archive path (`romm/src/main/kotlin/app/foldcade/romm/RommClient.kt:957`) without making suspicious bytes the head until resolved.
- After a session, “nothing changed” alone is normal. If another **already granted**, identity-matching candidate folder changed while the bound folder did not, that is a strong mismatch signal; capture both and show the paths/time. Do not crawl arbitrary storage, select the newest unrelated save or count Foldcade's own placement as emulator activity. Logs must be newer than their pre-launch baseline and attributable to the session/process. Old logs, restored mtimes and directory-only mtimes can all mislead.
- A modern filesystem mtime or a live log proves activity, not successful in-game save consumption. Use provider open/write/close events where Foldcade owns the provider; a writer can hold a descriptor across Home. Take stable bounded snapshots after writes quiesce, retain older versions on read errors, and retry after a known flush. No emulator in this audit exposes a universal stock, trustworthy “all game saves are flushed” callback.
- Reinstall/data-clear/reflash can preserve only one side: emulator files/settings, Foldcade's marks/ledgers, shared storage, hosted saves or Android grants. Check install changes and missing/replaced root markers. Do not clear a local record because data disappeared; verify RomM's history and restore its head. Foldcade setup exports intentionally omit grants, save marks, staged saves and ledgers (`docs/persistence.md:54`), but whole-device restore, shared-folder restores and reinstall combinations still require these checks.

Automatic repairs below all use the RomM-first contract. Mutate a working copy only after the emulator has released it or an explicit flush/quiescence handshake makes replacement safe; otherwise guide the user to exit the game normally and resume the repair afterward. A Home/background event alone does not establish that condition. A root URI in a log/config is **not permission** to open it: reuse a suitable held grant, otherwise request an Android folder grant. A retained emulator grant cannot be transferred to Foldcade or vice versa. Preserve and remotely verify every changed local copy before replacing; if there are conflicting candidates, let the user select progress rather than selecting by mtime.

## Beyond stock: maintained-build feasibility and safe migration

The preferred order is stock hooks, small upstream interoperability patch, then a maintained build **only where the first two cannot provide reliable safety**. A fork does not itself solve save identity, state/battery mismatches, multiple devices or upload receipts. Aim for a tiny shared contract: query actual game/profile/save destinations, accept a session-scoped working-copy URI with real grants, report the files actually read, and report successful flush with session generation and hashes. Grant-scoped access must not export emulator accounts, keys or unrelated config wholesale. A read-only endpoint can still disclose private information, so use explicit consent/caller checks.

`docs/apk-plugins.md:1` describes separate APKs; it currently recognizes Moonlight's platform and `gamestream` scope, not arbitrary emulator save plugins. A new emulator APK requires extending discovery/platform routing, save scopes/receipt protocol, registry/signature pins and update gates. Keep GPL code in its separate APK/repository, preserve source/license obligations, and use documented Android IPC. The host's current asset limit is 128 MiB. Do not link GPL native emulator code into MIT Foldcade merely to avoid a package boundary.

### Migration completion criteria

A differently signed/package-named app cannot read the old app's private files just because both implement the protocol. Obtain user-mediated SAF/export access from the old emulator or a small upstream export/provider bridge. If the only newer save is inaccessible, stop that game's migration and guide; installing the new build and booting an empty game is not a recovery strategy. Leave the old app/data installed until verification is complete.

1. Enumerate **all games/accounts/cards**, including unsupported aliases, excluded slots, states and locally played games absent from RomM. Find or explicitly create/link their RomM identities; raw shared-card/NAND/state archives can be held off-device without falsely declaring them compatible per-game heads. A known missing record or unreadable private save means migration is incomplete.
2. Upload distinct local progress to RomM, verify server hashes/IDs, and select heads with conflict/regression handling. Offline queued data has not completed this step. Keep the old working copy too.
3. Provision the new build's required BIOS/keys/firmware from RomM. Existing placement coverage is in the table; add guided import for gaps rather than requiring the old device. Preserve uniquely needed console/account data in a verified off-device export as appropriate.
4. Grant new package/host access separately, select profile/card/core, disable automatic state resume for the first restore, and place verified RomM heads. Migrate ordinary settings selectively. Losing graphics drivers, shader caches, controller mappings and UI preferences costs reinstall/recompile/re-setup; it should not cost game progress.
5. Verify that the new emulator actually opened the intended save files and flushed a subsequent save; verify that version reached RomM and remains recoverable through Y › Saves. Offer rollback to the old app with no deletion. Never auto-uninstall it as part of this research/design.

## Open questions and recommended decisions

- **What warrants a launch interruption?** Recommend block the ordinary launch for positive path mismatch, unreadable known save, unplaceable known server head, or a protected save missing at the proven destination. Offer a clearly explained per-launch at-risk choice. “No files changed in a short session” alone should generate neither a block nor a false lost-save alarm.
- **Which head wins after finding two live/local histories?** RomM remains authoritative, but preserve every differing local history there before selecting a head. If newly discovered bytes might contain unuploaded progress, show a recoverable choice; do not silently replace them or promote a fresh initial save above established progress.
- **Can unknown service coverage count as safe?** Recommend no. Show Unknown for DroidDeck/GameNative/Android/host-cloud coverage until an actual per-game status/receipt is available. A store badge and `Fine` are not evidence.
- **Should local-only games require a full duplicate ROM upload?** Recommend explicit association to an existing verified RomM ROM record first; when absent, a deliberate server catalog/import flow is needed. Do not invent a save-only API without checking RomM support. Offer an off-device archive/export path while integration is pending.
- **Which maintained build first?** Recommend try stock PPSSPP pinning, then upstream bridges for melonDS and the EX framework. Azahar's urgent incident can be substantially improved with fresh log/candidate verification and guided recovery now. DuckStation and Snes9x EX+ require separate permission for the contemplated modified distributions; do not silently substitute another product/fork.
- **What remains unverified?** No emulator/session was exercised; APK intent behavior is source-verified only where stated. Current DuckStation Android frontend source was unavailable, EX/Eden exact release cadence and some current menu grouping were not established, and current source revisions differ from several installed APKs. Root preference observations cannot become production implementations. Build times/dependency closure were not measured. No user answer is required to implement the highest-ranked safety improvements; version-specific QA is required before shipping any hook or automatic repair.
