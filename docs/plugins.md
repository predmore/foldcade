# Plugins

The contract lives in `:api` ([MIT](../api/LICENSE)). The host that loads it is `:host`. Samples are `:plugins:sample` and `:samples:out-of-tree`.

## Stability

`:api` is unstable. Any release may change it without a major bump. It stays unstable until a plugin outside this repository depends on it.

- The versioning rules below are the intended contract. No tool checks them yet. There is no binary-compatibility dump.
- Only the plugins in this repository are loaded on a device. `:samples:out-of-tree` is loaded from a jar in a JVM test. Android has no path that loads a plugin from another package.
- `Session`, `Panel`, `DisplayAssignment`, and the RomM credential ids live in `:app`. A plugin that depends on `:api` does not depend on them.

A change to `:api` should still keep the in-tree plugins and both samples compiling, and keep `PLUGIN_API_VERSION` and `PLUGIN_API_MINOR` honest.

## Contract

A plugin is a `PluginEntry` (`app.foldcade.api.plugin.PluginEntry`). One entry may contribute to any of four slots. The host stores each contribution in its own slot. A library and a metadata provider from the same entry stay separate objects.

- `platforms` — a system a library can classify a game into. `id` is canonical. `aliases` are other ids that mean the same platform.
- `players` — an installed app that runs a game for a platform.
- `libraries` — a source of games and saves (`LibraryBackend`). This is not a metadata provider.
- `metadataProviders` — titles, short text, and artwork (`MetadataProvider`). `cached` stays synchronous. `fetch` is the cancellable read. `Artwork.uri` is loaded as that string. A provider must not put a username, password, or token in it. `credentialFreeArtworkUri` removes userinfo and credential query parameters before the provider builds `Artwork`. The hero and the grid tile show the first `Cover`. A provider's cover loads through the RomM client, so a cover on any other origin does not load. When no provider has a cover, the shell's art sources look the game up: Steam's CDN for a GameNative Steam game, libretro's thumbnails for a ROM, the connected RomM server's cover search, then SteamGridDB when the user has saved a key (Settings › Library & data › SteamGridDB). RomM cover search works without a library entry and uses the server's configured providers and the existing RomM token. Both title searches accept an exact normalized name only, so an app such as Desktop keeps its mark instead of taking the nearest game's art. Search-result images load over `:net`'s `PublicHttps`. With no cover, the tile keeps its mark. The top screen also reads a provider's `Background`, `Logo`, and `Screenshot` for the focused game, before the shell's sources: wide art fills the screen with the logo over it, and a screenshot is drawn crisp beside the cover. RomM cover search supplies covers and square art; hero and logo sources remain separate.

The service file name is `META-INF/services/app.foldcade.api.plugin.PluginEntry`. That name is part of this contract.

`PluginHost.load` reads every entry that class loader advertises. The caller supplies the loader. This is the path for a bundled jar and for an out-of-tree jar. It does not discover or open an installed package. `load` runs off the main thread. One bad provider is recorded in `rejected` and does not stop the providers that follow. `load` does not throw, except `VirtualMachineError`.

`apiVersion` must equal `PLUGIN_API_VERSION` (1). The host rejects a different major. Set `apiMinor` to `PLUGIN_API_MINOR` (13). That is the additive revision this plugin was compiled against. The host loads a minor less than or equal to its own and rejects a newer minor. The interface default is 0, so a plugin that does not declare a minor still loads, marked as an older minor.

Public value types in `:api` are frozen data classes, or sealed interfaces whose leaves are frozen data classes. Adding, removing, reordering, or changing the type of a constructor property bumps the major. Adding an interface member with a default body bumps the minor and does not bump the major. Open enums and sealed types must be branched with an `else`. Adding a value there bumps the minor. Any other enum or sealed type in the module is closed. Adding a value there bumps the major.

The host calls `PluginEntry.bind` after validation and before the entry is stored. `CredentialAccess` opens credentials only for plugin ids this entry contributed. The default does nothing, so an older plugin minor of this major stays loadable.

Library I/O and metadata fetch are suspending. An implementation must stop that work when the calling coroutine is cancelled, and must rethrow `CancellationException` rather than wrap it in `PluginException`. The shell calls `ensureLocal`, then `prepareLaunch`, then `reconcile`, in that order. For a launch that opens another library's copy of the same file, it calls `prepareSaves` in place of the first two.

A library can report what it is doing with a game through `observeActivity` (API minor 4): `GameActivity.Downloading` with bytes so far and the total when known, `Checking`, `SyncingSaves`, `Synced` with the `SyncResult`, or `Idle` when the work ended with nothing to show. The host calls `observeActivity` once, before `connect`. Report from any thread and return at once. The shell shows it on the game's tile and on the top screen, and never stops the player for it. The default does nothing, so a library that reports nothing still lists and launches.

A metadata provider can list a game's achievements through `achievements` (API minor 5): each `Achievement` has a title, an optional description, points, a credential-free badge address, and whether the user has earned it. Set `GameAchievements.progressKnown` to false when you have the list but not the user's progress, rather than failing. The command center beside a running game shows the count and opens the list. The default returns null, so a provider without achievements still loads.

A library can also hold a save conflict for the shell (API minor 6). `pendingSaveConflicts` lists both copies, each with its source, time, and size. `resolveSaveConflict` applies keep-this-one, keep-both, or decide-later. Every choice keeps both copies. Decide-later stays out of the pending list until `reopenDeferredSaveConflicts`, which the shell calls on the next launch. The defaults do nothing.

A library can ask for setup and can have more than one configured copy (API minor 7). `id` stays the type. `instanceId` defaults to `id`, and the host keys the catalog and home tiles by it. `setup()` returns ordered steps: plain `Text`, a paste-only `Secret`, or `DeviceCode`. An empty list means nothing to set up. `configure(values)` is how stored text, including a RomM origin, reaches that instance. The host calls it before `beginDeviceCode` and before `connect`. Editing an origin calls `configure` again and then reconnects. The token stays in the credential store. Shared cache and data roots, platforms, and save bytes stay host-supplied. For the bundled RomM plugin those shared roots still arrive through `RommPlugins`. `Setup` and `DeviceCodePoll` are open. `DeviceCodeChallenge` is frozen. `beginDeviceCode()` takes no argument: the plugin creates the device identifier and keeps it beside `device.json`. `Approved` carries only the token.

A library that downloads games can delete one again (API minor 8). `removeLocal` deletes what `ensureLocal` downloaded, so the game is `RemoteOnly` and the next launch downloads it. Saves stay. The Y menu offers Delete download only for a `Cached` game. The default refuses with `Unavailable`.

A player can open games by path (API minor 9). `Player.opensByPath` asks the shell for a `LaunchTarget.SharedFile`: the absolute path of the game in shared storage, beside the content URI the backend returned. The shell builds it for a document of Android's external storage provider and for a RomM download in Foldcade's shared media folder. A game with neither has no path, and the shell does not start the player. `LaunchFlag.ReplaceRunning` marks a player that quits, rather than switch games, when handed a different one while it runs; the shell starts that intent again if the player quits within moments. `SaveFolderHolder.saveFolderKey` lets several players share one save folder, which the shell asks for and lists once, and `suggestedSaveFolder` is where the picker opens. `saveFileName` may name folders below the save folder, separated by `/`; the shell creates them. The defaults keep the earlier behaviour.

Two libraries can have one game (API minor 10). `fileName` names the file a game opens as, such as `Tetris DS (USA).nds`, even before it is downloaded, or null for a game of several files or one the library cannot name offline. Players name saves after that file, so the shell shows copies with the same platform and file name as one tile. It plays a copy already on the device, and keeps the saves with the first server's copy whichever copy opens: it calls `prepareSaves(game, player, target)` on that copy with the target of the one that plays, then `reconcile` on it as usual. The default `prepareSaves` calls `prepareLaunch`, which may download that library's copy too; a library that keeps saves apart from its download overrides it. The default `fileName` is null, which never folds.

A player can keep a save as folders (API minor 11). `saveFolders(slot, romFileName, romHeader)` names them below the save folder, each as a `SaveFolderPart` with the name its files have in the zip, and `romHeaderSize` is how many bytes of the game file the shell reads for `romHeader`; Azahar reads the title id from a CCI's header. The shell moves the folders as one zip, under the same checks as a single file: unseen changes are handed over first, replaced files are backed up, and a placement is read back and undone when it does not match. Placing a zip makes each folder it holds match it and leaves the rest alone. The defaults, 0 and null, keep a slot to one file.

A player can ask for firmware (API minor 12), and name what its save folder holds. `SaveFolderHolder.saveFolderMarkers` lists names one of which the player's folder has, such as DuckStation's `memcards` and `bios`; the shell does not keep a picked folder that has none of them, and asks again. `firmwareFileName(name)` names where the player looks for a firmware file, such as a console's BIOS, below its save folder, or null for a file it does not use. That folder is the one the user picked for the player, or else the one its save declarations name. A library that has that firmware for the game's platform downloads and checks it in `prepareLaunch` or `prepareSaves`, and returns it in `LaunchTarget.ContentUri.firmware`. The shell writes each one into the player's folder and reads it back. It replaces a file there only when that file still holds what the shell last wrote, so a library's new copy follows and a file the user put there stays. A failed write does not stop the launch. The default, null, asks for none.

A player can choose which firmware to take (API minor 13). `firmwareHeaderSize` is how many bytes from the start of each firmware file the shell reads. `chooseFirmware` picks from those `FirmwareOffer`s, each the file's name and that header, or returns them all. `FirmwareOffer` compares the header by its bytes. A firmware file that is a zip is also offered as the files inside it, named `<zip name>/<file name>`, the file's own name whatever folder the zip keeps it in. `firmwareFileName` may be given that pair. A library opens a zip only when the player wants the zip's own name too. A player that wants files from a zip should name the zip as well and leave it out in `chooseFirmware`. A player that does not want files from a zip returns null for a name that holds `/`. The shell writes only what `chooseFirmware` returns. A player that throws writes nothing, and a failed write still does not stop the launch. The defaults, 0 and every offer, keep the earlier behaviour.

A player can find a save by the folders' names (API minor 13). `findSaveFolders(slot, game, folder, forLaunch)` is asked before `saveFolders`. `game` reads the game file at any offset. `sibling(name)` is another file in that same folder, such as a cue sheet's track or the disc a playlist names. It is null when there is no such file, or the shell cannot reach the folder. A name that contains `/` or `\`, or is `.` or `..`, is null. The shell resolves it for a document in a tree: a RomM download, whose files share one folder, and a file in a folder the user picked. A content URI that is not in a tree has no sibling. `folder` reads and writes the save folder by paths below it. `read(path, offset, length)` reads part of a file: up to `length` bytes from `offset`, fewer at the end, or null when it cannot be read. `write` copies an existing file into Foldcade's save backups before replacing it, when the bytes differ, the same copy `moveToBackup` keeps. When `write` returns false, the file may hold part of the new bytes, and its old bytes are in the backups. Backups keep the newest 20 files per player. The result is a `SaveFolderSearch`: each folder directly below `parent` whose name, upper-cased with `-` and `_` removed, contains `nameContains` written the same way. A name that starts with `_` is never a match. PCSX2 keeps a deleted save as `_pcsx2_deleted_<name>`, and a real save folder does not start with `_`. The shell moves the matching folders as one zip, each under its own name, with the same checks as `saveFolders`. Placing makes each folder the zip holds match it and leaves every other folder alone, and a zip whose first-level names do not all match is refused. The player may set the folder up only when `forLaunch` is true, and must leave anything that holds saves as it is. The shell asks again on the way back with `forLaunch` false, and then only reads. A throw on a launch, including a setup the player started and could not finish, means the save could not be placed: the game does not start. A throw on the way back means no spot. A setup that changes the folder counts as a placed save: the player starts fresh. `saveSyncState` says whether the saves sync, for Settings. The folder is read only there, and a write returns false. `SaveFolderEntry.size` is 0 when the provider does not report a size. `SaveSyncState` is open: `Syncing`, or `NeedsSetup` with the steps the user follows once in the player's own settings. Null means the player does not say. The defaults, null, keep a slot as it was.

A player can say what is left before it can start (API minor 14). `setupSteps(folder)` is what the user does once in the player, such as finishing its first-run setup and installing the console's firmware, or null when it can start. The folder is read only, and null when the user has not picked one; a player that checks its setup through that folder then says how to pick it. The shell asks before every start of a `SaveFolderHolder`, from RomM or a local folder, after it has placed saves and firmware, and does not start the player while this says what to do: it shows the steps, with Open for the player. Settings shows them too, once a folder is picked. `needsFirmware(folder)` is false when the player no longer needs the firmware its library has, such as a console firmware it has already installed from that file, so the shell does not write it again. The folder is read only. The defaults, null and true, keep the earlier behaviour.

A player whose saves no other app can read can have the shell keep them (API minor 12). A `HostedSaveFolder` gets a folder in Foldcade's storage, offered in Android's folder picker as **Foldcade**, with `hostedFolderTitle` as its summary. The user picks it once in the player's own settings, following `hostedFolderSteps`, and the player then reads and writes its saves there through the grant the picker gives it. Document ids are paths, `foldcade:<player id>/<path>`, as Android's own storage writes them. `bindHostedFolder(contentUri, inUse)` passes the folder's tree URI and whether the player holds a grant to it. Until it does, the player declares no slot there, and the shell asks before a server launch, at most until the user chooses **Not now**. DuckStation uses it for its memory cards.

`openLibrary` adds a copy after load. The host mints ids such as `romm#2`. A type id may not contain `#` or `:`, and registration refuses `#`. The host refuses the result unless `id` is the requested type and `instanceId` is the minted id. The default RomM instance stays `romm` with credential key `access-token`. Another server adds `access-token@romm#2` under the same plugin id. Removing one server calls `forget` on that key, never `forgetPlugin("romm")`. A second account on the same canonical origin is refused. `https://host/` and `https://host/api` are one server. Local folders stay one forest on `local-folder`. One `romm.metadata` slot routes each game by `backendId` to that instance's connection and catalog.

Setup runs again only when nothing is stored, when credential lookup returns `Unreadable`, or when connect throws `NotAuthenticated`. Not on `Unavailable`, and not on a network error.

RomM recovery opens the saved connection that failed and replaces only its token. Refreshes run independently, with at most three servers loading at once; a new refresh cancels the previous one. Artwork routes to a configured server by origin and base path, with a separate client and cache per server. Cover search for games outside RomM uses the first saved server, including an additional server when the original has been removed.

Plugin authors may choose any license for their original work. The API, bundled plugins, and samples are MIT licensed; retain the MIT notice when reusing their code. See [licensing](licensing.md).

## Emulators

`:plugins:emulators` (`EmulatorsEntry`) holds the standalone emulators for the platforms the local-folder catalog classifies, other than the DS and 3DS. `EMULATORS` is one table: application ids, activities, the intent action, and whether the game URI goes in the intent data or in a string extra. Package ids, activities, and handoffs are read from ES-DE's Android find rules and system list.

- Each emulator becomes one player per platform. The player id is `emulator.platform`, such as `dolphin.wii`.
- Players for one platform keep the table order. The shell launches the first one with an installed package (`preferredPlayer`). With none installed, the missing-player dialog names the first one and lists every package.
- The game is always a content URI with a read grant. When the emulator reads it from an extra, the same URI is also the intent data, because the shell grants read on the data only.
- A launch that needs a file path is not in the table. RetroArch has its own plugin.
- The entry declares no platforms and no save slots. These players do not ask for a save folder.
- Every application id must be in the app manifest's `<queries>`. `PlayerLaunchTest` checks that.

Before an Eden game starts, the shell checks the installed Eden package. `EDEN_PACKAGES` is that list, and the table uses it too. Eden keeps keys and firmware in its private data directory and publishes the directory through its own documents provider, `<package>.user`, with root id `root`. When Foldcade has no grant on that root, has not asked yet, and a connected RomM server has Switch `prod.keys` or a firmware zip, the shell offers the folder once. The offer says to choose Use this folder at the bottom, without opening a folder inside it. **Not now** still starts the game, and a later launch does not ask again. A folder that is not the installed Eden package's root offers **Try again** and **Not now**. **Try again** opens the picker at that root and keeps a held launch, so a correct pick starts it. **Not now** marks the offer answered and starts a held launch. Backing out of the picker does the same. A RomM or network error starts the game and does not count as declining. With the grant, the shell adds `keys/prod.keys` when it is missing or empty, and firmware `.nca` files under `nand/system/Contents/registered/` when Eden has none. It adds `keys/title.keys` in that same pass when RomM has it and Eden does not. A missing `title.keys` alone does not contact RomM. An existing keys file or firmware is never replaced. When that pass adds a file, the shell does not start the game. It asks the user to restart Eden once, and that prompt returns on each Switch launch until Eden has been force-stopped or the device restarted. The pending restart is the package name and the device boot count. It clears when the boot count changes, or when Eden is in Android's stopped state, which Force stop sets and the next start of Eden clears. An unknown boot count, -1 on either side, counts as unchanged. That check runs before the shell opens Eden's documents provider, because opening it starts Eden and clears the stopped state. Continue opens Eden's App info. **Not now** only closes. Neither answer clears the pending restart. Eden reads keys and firmware only when it starts, and Foldcade can't restart it. After a force stop or a reboot, the next launch starts the game. The firmware download shows on the game's tile the same way a game download does. A failed copy is logged and the game still starts; the next launch tries again, because the file is still missing. Settings › Emulators › Eden keys and firmware opens the same picker with no launch waiting behind it, and only while Eden is installed and a RomM server is signed in.

### Table or own plugin

An emulator goes in the table when its launch is data only: application ids, activities, an action, a handoff, fixed extras, and flags. An emulator that needs its own code gets its own plugin, the way `:plugins:aps3e`, `:plugins:azahar`, `:plugins:armsx2`, `:plugins:duckstation`, and `:plugins:melonds` do. Own code means save slots or a save folder, both displays, extension rules, or a launch the table cannot express. An emulator in the table that gains one of these moves out to its own plugin.

The host stores an entry whole or not at all. One bad row in the table drops every emulator in it. `EmulatorPlayerTest` checks that ids are unique, and `ShellHostTest` checks that no bundled entry is rejected.

## RetroArch

`:plugins:retroarch` (`RetroArchEntry`) is RetroArch, `com.retroarch.aarch64`, `com.retroarch`, or `com.retroarch.ra32`, in that order. `SYSTEMS` lists one row per local-folder platform with the libretro cores to start, best first. Each row becomes a player, `retroarch.<platform>`.

- The launch starts `RetroActivityFuture` with string extras: `ROM` is the game's path, `LIBRETRO` the core in RetroArch's `cores/` directory, and `CONFIGFILE`, `DATADIR`, `SDCARD`, and `EXTERNAL` are what RetroArch's own launcher passes. RetroArch 1.22 reads only these, opens games only by path, and does not read the intent data. The player sets `opensByPath` and `ReplaceRunning`.
- A missing core leaves RetroArch on a black screen. The shell keeps `RetroArchCores` current through a tree the user grants on RetroArch's documents provider (`<package>.documents`, whose root is RetroArch's data directory). Nightly builds also answer a `com.retroarch.QUERY_INSTALLED_CORES` broadcast, but any app can send its reply, so the shell does not use it. `coreChoice` is the first installed core, a missing one, or unknown. The shell asks once to see the cores, names a missing core, and checks RetroArch's storage permission before a start.
- With a core installed, RetroArch goes ahead of a standalone emulator for its platform, except the DS (`aheadOfStandalone`). Without one, it gives way.
- Battery saves are `<save folder>/<core library name>/<game>.srm`, RetroArch's default. Every player shares one save folder, keyed `retroarch`. RetroArch tells games apart by the `ROM` and `LIBRETRO` strings, and `freshStart` names the same core the other way, through `/data/data`. The shell keeps a key for the last intent it started per package. A start normally repeats that spelling so the game resumes; after the shell writes a save the player has not started with, it uses the other one, so RetroArch quits and starts fresh with the new save.
- Every application id must be in the app manifest's `<queries>`.

## Moonlight

`:plugins:moonlight` (`MoonlightEntry`) is the official Moonlight client, `com.limelight`. The player starts `com.limelight.ShortcutTrampoline` with the host UUID and a string `AppId`. The plugin does not pair, and it does not open Moonlight's database; the app pairs on its own behalf (below). Moonlight does the rest of a start itself: it wakes a sleeping computer it knows the MAC address of, asks before quitting a different running game, and resumes the same one. The UUID must be sent in the case Moonlight stored it, since its lookup is case-sensitive.

Moonlight puts a game on the home screen by asking Android to pin a shortcut. Android sends that request to the default home app only, and it tells Moonlight pinning is unsupported unless the home app handles `CONFIRM_PIN_SHORTCUT`. `PinShortcutActivity` handles it. It accepts a Moonlight game shortcut without asking, because the user just chose Create shortcut, and it leaves every other request unanswered. After accepting, Foldcade reads the game back from Android's pinned shortcuts, not from the request, and places it in the Moonlight folder, even with Add new games off.

A launcher never sees a shortcut's intent, so `readMoonlightShortcuts` reads the host and app from the shortcut's id and label. Moonlight's game shortcut id is the 36-character host UUID followed by the app id, and its label is the app name followed by the computer name in parentheses. Moonlight's dynamic computer shortcuts, with the host UUID as id and the computer name as label, tell the parser which suffix to take off a label. Disabled shortcuts are skipped; Moonlight disables a game's shortcut when its host or app goes away.

`MoonlightLibrary` lists the enabled pinned game shortcuts Foldcade last read, then the apps of each computer Foldcade paired with itself. A game in both is listed once, as its pin. Every pin is on Home in the Moonlight folder; a listed app follows **New games on Home**. There is no import step and no source setting. Hide keeps Foldcade's Android pin. Only the hold-confirmed Delete shortcut row drops it with `LauncherApps.pinShortcuts`, and only a pinned game has that row (`ShelfGame.shortcut`).

The last read is saved, so Moonlight tiles keep their names at start. Their tile ids are the bare remote key, not a `lib:` id, so the shell keeps them on Home, hidden ones included, until the first live shortcut read. A Moonlight game is taken off Home only once Android says its pin is gone.

`MoonlightArt`, the entry's metadata provider, gives each game the box art Moonlight already keeps. Moonlight's exported `PosterContentProvider` serves it read-only at `content://poster.com.limelight/boxart/<host UUID>/<app id>` once Moonlight's game list has shown the game. A launcher cannot list that provider, so the app checks each address once (`moonlightPosterExists`) and loads only addresses of that exact shape. A game Moonlight has no poster for falls through to the public sources.

`MoonlightHosts` in the app watches Moonlight's computers while a Home screen is shown and Moonlight is installed. Moonlight's dynamic computer shortcuts name each one when Foldcade is the home app. It finds them, and computers no shortcut names, by mDNS (`_nvstream._tcp`, which Sunshine and Apollo advertise), or a named one by its name in DNS, then asks `/serverinfo` over plain http through `:gamestream` and `LanHttp`, which reach LAN addresses only. That needs no pairing. An answer counts only when its `uniqueid` is the host's UUID. Sunshine names the app it is streaming there, so that tile reads **Running on** the computer, with the paused badge; Apollo does not say over http. The top screen's line names the computer, or says it is offline once a computer that answered stops.

### Pairing

Settings › Library has a **Games from** switch for each computer the watcher knows: Moonlight's, the ones mDNS finds while Moonlight is installed, and the ones already paired. Turning it on pairs Foldcade as a GameStream client of its own (`:gamestream`'s `GameStreamPairing`, the steps Moonlight's `PairingManager` takes and Sunshine's `nvhttp.cpp` checks). Foldcade shows a four-digit code; the user types it into Sunshine's or Apollo's PIN page. A host whose answer does not match the code, or whose secret is not signed by the certificate it sent, is refused. Each attempt uses a fresh `uniqueid`, because Sunshine holds an abandoned one for five minutes and knows a paired client by its certificate.

`GameStreamIdentity` keeps the client key in Android's keystore with a self-signed certificate, as GameStream clients use. Besides signing, the key allows raw RSA decryption with no padding: Conscrypt signs a TLS 1.3 handshake with a keystore RSA key that way, and without it the handshake fails with `INCOMPATIBLE_PADDING_MODE`. Settings move to a new device and keys do not, so saved pairings carry the fingerprint of the key they were made with and are dropped when it differs.

Once paired, `LanTls` trusts only the certificate the host gave while pairing, and presents this device's. Every five minutes while Home is shown, a paired host that answers is asked for `/applist` over https. When its plain-http `/serverinfo` names no running app, it is asked over https too, since Apollo names its running app only to a paired client. A host that stays missing is looked for less often, down to every five minutes. Box art comes from Moonlight's poster first, then the host's `/appasset`, kept in the cache. Forget drops the pairing, the host's apps, and its art. Sunshine has no way for a client to unpair itself, so the user removes Foldcade from its client list.

`reconcile` does nothing. RomM does not configure this library, and reconcile does not call RomM. The official client does not take both displays. The stream starts on the screen the picker targets, and the other screen keeps the picker.

## DroidDeck

`:plugins:droiddeck` (`DroidDeckEntry`) is DroidDeck, `com.droiddeck.launcher`, which runs Valve's ARM64 Steam client on the device. The player starts `com.droiddeck.launcher.MainActivity` with action `com.droiddeck.launcher.LAUNCH_GAME` and the game id as a string `app_id`, and no `game_source`. The id is Steam's 64-bit game id. It is a Steam app id for a Steam game, and a value past an int for a game added to Steam from outside it, so it is never sent as an int. With no game id the player opens DroidDeck's own front end; DroidDeck's own tile in the Emulators folder on Home opens it that way. DroidDeck starts Steam when it is not running, hands a running Steam session the game, and returns home when the game ends. A game DroidDeck does not have, or a busy session, is DroidDeck's own message.

DroidDeck has its own platform, not `pc`, so a DroidDeck game always opens in DroidDeck and a GameNative game always opens in GameNative, with both installed.

Games reach `DroidDeckLibrary` two ways:

- **Add to home screen.** DroidDeck pins a shortcut, which reaches `PinShortcutActivity` the same way Moonlight's does. Its id is `game:` and the game id, its long label the whole name. `readDroidDeckShortcuts` reads enabled pinned ones. DroidDeck publishes no dynamic shortcuts. Hide keeps Foldcade's pin; the hold-confirmed Delete shortcut row drops it. Unpin, on a Home shortcut, does not, since the game stays in its folder.
- **Game-file sync.** DroidDeck can keep a folder of `.steam` files in step with its library. Added as a library folder, it is recognised by the `.droiddeck-sync.json` inventory DroidDeck keeps there, and every `.steam` file beside it is a DroidDeck game.

`routeSteamFiles` splits the folders' `.steam` files. A file DroidDeck synced, or one with an id past an int, goes to DroidDeck. Any other goes to GameNative, unless DroidDeck is the only one of the two installed. Installing or removing either app routes them again.

Pinned games come first, so a pin keeps DroidDeck's whole name over the 40-character file name. Tiles are `droiddeck.` and the game id, in the DroidDeck folder. The last shortcut read is saved, and the shell keeps DroidDeck tiles on Home until a live shortcut read and a finished folder scan have both reported. Art comes from Steam and SteamGridDB by app id for a Steam game, and by title for any other.

`reconcile` does nothing. Steam Cloud keeps the saves. The entry has no metadata provider. Read from DroidDeck `de1a734`; see the player's KDoc for the files.

## Samples

`:plugins:sample` (`SampleEntry`) is the in-tree sample. It implements the four interfaces and does nothing else. Library and metadata are separate objects so the host can store them in separate slots.

`:samples:out-of-tree` (`OutOfTreeEntry`) compiles against the API module only. The host does not compile against this module. It is loaded from its jar through `PluginEntry`, the same entry an external plugin uses.

## Reserved RomM ids

`romm` and `romm.metadata` belong to the built-in RomM entry, `app.foldcade.plugins.romm.RommEntry`. Another entry cannot take them, even if it is registered first. The exemption is that class object on this host's class loader. A plugin loader can define a class with the same binary name. That object is a different class, and it is refused.

## Minify

Minify is off for debug and release. Bundled plugins are found by `ServiceLoader` from `META-INF/services/app.foldcade.api.plugin.PluginEntry`. If minify is enabled later, keep rules are required for that service file and for `PluginEntry`. Without them, R8 drops the file and the entry classes, and the host loads no plugins.
