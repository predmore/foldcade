# Save-sync candidate audit (4 November 2026)

This covers all 21 emulator rows in the original shared table. Foldcade collects no Thor emulator-usage counts, so **demand below is an estimate**, not a measured player count. PSP and GameCube come first as requested; next priority balances likely platform demand against source-verifiable, isolated saves. On the shared Thor, only NetherSX2/AetherSX2 and EmuCoreX from this table were installed before QA. Neither PSP nor GameCube exists in its current RomM catalog (38 games).

The follow-up preserves this ranking: Flycast access was checked first and could not be made writable without root; EX is implemented, then N64 and Pizza Boy are deferred for the access/verification limits below. Do not turn the unverified rows into declarations based on these estimates. A format without a reachable active folder still cannot sync safely. No implementation in this PR reads another app's private files by bypassing Android permissions.

## Flycast

Checked at `7adbf3caef251b153e348df3f469a0f35878339d`: [oslib.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/oslib/oslib.cpp) `getVmuPath` owns the filename and fallback policy; [option.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/cfg/option.cpp) defines `Dreamcast.VMUPath` and per-game VMU defaults. Only A1 can be isolated: upstream does not create per-game files for the other ports. `UsePhysicalVmuMemory` also leaves the disk VMU unresolved. Shared VMUs never belong to one game. [settings_controls.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/ui/settings_controls.cpp) puts Per Game VMU A1 and Use Physical VMU Storage under Controls.

[reios.h](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/reios/reios.h) and [emulator.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/emulator.cpp) define the IP.BIN product-number field and trimming; [gdi.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/imgread/gdi.cpp) and [common.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/imgread/common.cpp) define track offsets and raw sector layout. [Android.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/shell/android-studio/flycast/src/main/jni/src/Android.cpp) uses home `data/`. [BaseGLActivity.java](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/shell/android-studio/flycast/src/main/java/com/flycast/emulator/BaseGLActivity.java) fixes the live Android home to `getExternalFilesDir(null)` (internal files only if unavailable). [AndroidStorage.java](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/shell/android-studio/flycast/src/main/java/com/flycast/emulator/AndroidStorage.java) implements Home Folder Import/Export as copies, without retaining a grant or changing the live home. A correct implementation would need writable access to `primary:Android/data/com.flycast.emulator/files`; shared exports and all-files provider aliases cannot substitute for it. Thor’s real picker granted that exact tree, but `DocumentsContract.createDocument` in its `data` directory failed with `Permission denied`, as did the non-root shell. This revision therefore leaves Flycast launch-only. The [disc loader list](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/imgread/common.cpp) has no ISO loader; a future identity reader can resolve GDI track 3, while CHD/CDI/CUE need their own readers. Legacy root/ROM-name copies must not be treated as the current write location. The same holds for a custom VMU directory whose fallback still holds the save.

[maple_devs.cpp](https://github.com/flyinghead/flycast/blob/7adbf3caef251b153e348df3f469a0f35878339d/core/hw/maple/maple_devs.cpp) keeps the VMU open in `rb+`, writes with `fseek`/`fwrite` without `fflush`, and closes on unload. The user must unload the game before returning or replacing saves, so the final write is flushed and an old buffer cannot later overwrite a placed VMU.

### N64 access decision for the follow-up

[CoreService.java](https://github.com/fzurita/mupen64plus-ae/blob/f3c381bcc58e4adce897aba323193d3f407e30e3/app/src/main/java/paulscode/android/mupen64plusae/jni/CoreService.java) shows external-storage mode importing to private GameData at startup and exporting at shutdown. Import keeps existing private files; export deletes the private copy only after successful copying. Thus external storage is not a safely authoritative active save after a crash, failed export, or while the game remains open. The [manifest](https://github.com/fzurita/mupen64plus-ae/blob/f3c381bcc58e4adce897aba323193d3f407e30e3/app/src/main/AndroidManifest.xml) exports no save-tree provider. Without root or a new upstream handoff, Foldcade cannot back up the potentially newer private copy before replacement. FZ/AE remain launch-only.

### EX storage and companions corrected in the follow-up

[Android ApplicationContext.cc](https://github.com/Rakashazi/emu-ex-plus-alpha/blob/1c12fac5ce49badaadff2e2f210dcc30b89f4943/imagine/src/base/android/ApplicationContext.cc) makes `storagePath()` the package external-files directory on current Android. Therefore App Folder is `Android/data/<package>/files/EmuEx/<shortSystemName>/saves`, not shared `/sdcard/EmuEx`. The framework uses the ROM directory when no explicit save path is selected; a failed write is an error, not an automatic relocation. Foldcade discovers known shared choices only with the emulator’s exact grant; private App Folder requires a reachable SAF grant or a manual shared-directory choice. Retained grants cannot prove the private current-path setting, so custom choices must match in both apps.

[GBC Main.cc](https://github.com/Rakashazi/emu-ex-plus-alpha/blob/1c12fac5ce49badaadff2e2f210dcc30b89f4943/GBC.emu/src/main/Main.cc) separately loads and writes `.rtc` as four big-endian bytes. [EmuApp.cc](https://github.com/Rakashazi/emu-ex-plus-alpha/blob/1c12fac5ce49badaadff2e2f210dcc30b89f4943/EmuFramework/src/EmuApp.cc) and [EmuSystem.hh](https://github.com/Rakashazi/emu-ex-plus-alpha/blob/1c12fac5ce49badaadff2e2f210dcc30b89f4943/EmuFramework/include/emuframework/EmuSystem.hh) map named battery slots to `<contentName>/saves/<slot>/auto.<extension>`; bundles include those batteries and omit state files. These files travel as one durable archive so the clock is never acknowledged independently of SRAM. On Thor, Main Slot mode could resume an autosave without running the boot path after a same-game battery placement; Main Slot (No State) loaded the placed battery correctly. Battery sync therefore requires that launch mode, rather than relying on the older-state warning. Foldcade does not rewrite EX’s private preference.


[Snes9x memmap.cpp](https://github.com/Rakashazi/emu-ex-plus-alpha/blob/1c12fac5ce49badaadff2e2f210dcc30b89f4943/Snes9x/src/snes9x/memmap.cpp) calls `SaveSRTC()` from `SaveSRAM()` for S-RTC/SPC7110 clocks and writes 20 bytes to `.rtc`. [S9XApi.cc](https://github.com/Rakashazi/emu-ex-plus-alpha/blob/1c12fac5ce49badaadff2e2f210dcc30b89f4943/Snes9x/src/main/S9XApi.cc) maps that path through `contentSaveFilePath`, alongside the SRAM and inside named battery slots where applicable. SNES clock and SRAM files travel in the same durable archive.

### Pizza Boy verification limit

The official [Pizza Boy GBA](https://play.google.com/store/apps/details?id=it.dbtecno.pizzaboygba) and [GBC](https://play.google.com/store/apps/details?id=it.dbtecno.pizzaboy) distribution pages point to Play. No public upstream writer or official standalone APK was available for this batch’s store-free QA. `.sav` and `.rtc` names from secondary reports cannot establish current Basic/Pro encoding, clock semantics or active path. The follow-up adds no Pizza Boy declarations and installs no mirrored APK.
