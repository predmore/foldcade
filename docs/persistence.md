# Persistence audit

Settings and confirmed Home edits are restored from the app-private `foldcade` shared preferences. `SessionStore` owns those keys, and `ShellController.publish` saves changes made through controller input or the settings screen. Preferences use Android's asynchronous `apply`; save reconciliation markers and pending returns use `commit` before handing control to a player. Android flushes pending preference writes during component lifecycle transitions ([SharedPreferences documentation](https://developer.android.com/reference/android/content/SharedPreferences)).

## Saved choices

- Screens: Layout (Art top, Art bottom or Top only), the screen A plays on, and the default display's physical panel. These are portable choices for the Thor. An older Main screen Bottom choice migrates to Art bottom and Play on Bottom when no Layout was saved.
- Personalization: theme name, whether the background was explicitly selected, background motion, motion speed, and controller confirmation/dismissal choices per device.
- Sound: music enabled, volume, and track id. Theme and track selections fall back when unavailable without overwriting the saved choice during startup. Nonfinite volume values fall back to the default.
- Library: source folder URIs, RomM origin, All's order (A–Z or Recent), automatic placement of new games, and the artwork switch.
- Home: tile positions and empty slots, collections (folders the user made in older releases become collections, and the built-in Favorites of older releases becomes an ordinary one, or goes if it was empty and never renamed), confirmed names and icons, each folder's and collection's sort (in a row of its own, so an older release keeps the arrangement, which a sort never changes), hidden tiles and their former root/group slots, removed system folders with their root slots and games still filed in them, and when Recently played may first appear.
- Apps: installed apps are filed on the Home board like any game, in Android Games, Apps, or Emulators, and hidden there. Releases with separate Android shelves saved their own overrides; the first launch after them hides the apps hidden on a shelf on Home and forgets the rest.
- Emulator choices: each system's (`system_player:`, by canonical platform id) and each game's Open with (`game_player:`, by tile id), as a player id, an optional RetroArch core, and the name shown when it was chosen, in versioned Base64url fields. No entry is Automatic or Default. A choice whose emulator is uninstalled stays, so reinstalling brings it back. A tile formed from several copies also finds a choice saved under a copy's id; Default clears them all. A pending RetroArch save return keeps the core it launched with, so a later choice or core scan cannot move the read-back to another core's folder.
- Players: save folder URIs and whether detection found them, save hashes, and pending save returns. Playing without syncing applies to one launch and is never saved. Old skipped save-folder and hosted-save offers are removed on startup.
- Same games: `same_games` maps each copy of a game several libraries have (same system and file name) to the one tile it is shown as. It is kept when a copy goes away, so the tile keeps its id while a server is offline or removed. The Home board and art choices move onto the tile when it forms; play history stays under each copy's id and is read through the tile. Moving play off a tile moves every copy's.
- Onboarding: Home, library-folder, usage-access, and controller prompt answers.

Brightness, the Home role, notification access, usage access, and optional all-files access belong to Android. The shell reads their current state rather than restoring an app-owned copy. SAF folder URIs are saved after acquiring persistable access. Removing or replacing one folder reference keeps its grant while another saved source or player still uses that tree, including save folders named by documents inside it. Detection clears a found folder when its writable reach or required player grant goes away, or another reachable copy makes it ambiguous, and searches again, so missing-sync notices return. User-picked folders stay chosen; a missing grant unbinds them until access returns.

Found ROM folders (`found_roots`) and the ones already announced stay on the device; the folders a player removed (`removed_roots`) travel in a backup so they stay removed. Settings › Emulators › Auto-find saves, and Settings › Library › Auto-find games, open Android's all-files access page only on request. With access, detection can use Foldcade's private shared-storage provider after real SAF grants. Its document URIs use the same save reconciliation marks as SAF folders. Home resume re-reads access and detection; revocation clears found provider folders and tries SAF again. No saved switch can hide missing-sync notices, and explicit folder picks are never replaced. Android/data and Android/obb still need their own SAF grants.

## Home snapshots and startup

The Home format is versioned. Version 2 encodes each field separately as Base64url, so opaque game ids or names containing record separators cannot damage neighboring fields. Version 1 layouts still load and are upgraded on the next saved snapshot. Invalid version 2 records are skipped individually. Set and folder ordering is deterministic, and saving an unchanged snapshot skips the preference write.

A lifted tile is serialized at its last confirmed position. Confirming a move saves the new position; canceling or restarting during an unfinished move restores the original position. Open dialogs, rename drafts, editing state, and active external-app sessions are transient.

Saved Android, GameNative, Moonlight, DroidDeck, and library placements are retained while their respective catalogs load. An empty startup catalog does not establish that a game was removed, so a folder whose games are still loading keeps its place and its name. A reported catalog can then remove games that are actually gone.

No games, no folder. A folder Foldcade makes, for a platform or for Android, GameNative, Moonlight, or DroidDeck, appears with its first game. Filing a game into a collection never empties its folder. Hiding every game in an automatic folder removes that folder from the grid. A folder the user removed stays off Home until Show in Hidden. A new game brings back only a folder that disappeared because it emptied. Pinning a game files it into a removed folder without bringing that folder back. Folders hold games, not the apps that run them: an installed app a player plugin covers, such as Azahar, Dolphin, GameNative, Moonlight, or DroidDeck, goes in its own Emulators folder, under the same rule. Releases before the Emulators folder filed those apps under Android Games or Apps (once called Android Apps); each moves to Emulators once, and after that stays wherever the user puts it. User-made groups are collections, which stay, even empty, until the user removes them, which deletes them.

## Files, secrets, and transfer

Confirmed GameNative catalogs use the existing durable-file writer: write a temporary sibling, sync its bytes, replace the destination, and attempt to sync the parent directory. Play history is appended and synced under `files/play-sessions`, with each game's name at launch in `names.log` beside `events.log`, so Play activity still names a game that has left every catalog. A session removed from Play activity is one more `Removed` line, never a rewrite; readers leave that session out. Moving a game's play onto another (Y › Play time, after a ROM is renamed or replaced) is one `Moved` line per finished session, naming the game it counts for from then on; the session's own lines keep the game it was played as, a later `Moved` line wins, so Undo is one more line, and a build that predates `Moved` skips those lines and counts the time where it was played. Each played game's cover is kept as a small WebP under `files/play-sessions/art`, named by a hash of its id, when it is played or first drawn in Play activity, so a game no library has any more still shows its cover there. Nothing prunes the log, the names, the covers, or `art/choices.json` when a game leaves a catalog, so a game that comes back under the same id has its play, name, and chosen art again.

Settings › System › Backup › Play history exports the whole history as one zip the player keeps anywhere: `foldcade-play.txt` naming the format, `events.log` and `names.log` in their stored line formats, and `art/` with the kept covers. Import only adds: sessions the log lacks, whole (one that never ended is closed at its last event), then removals and moves it has not seen, then names for ids with none here, then covers this device lacks. Importing the same file twice adds nothing. Import reads only those entry names, caps each entry's size, and refuses a file without the marker or from a newer format. RomM's durable device/save data and replaced player-save backups remain under `filesDir`, as does `save-handover`, where a save kept as folders waits as a zip until its library has kept it; downloaded games and regenerable artwork bytes use cache storage.

Resource packs Foldcade did not ship live in `files/themes`. `files/theme-installs.json` records each archive, the updates kept beside them in `files/themes-previous`, and the [trials](themes.md#releases-and-trials) that put a crashing pack back. It is written with the durable-file writer. A restored backup puts every pack on trial once, since restored archives have new modification times.

A confirmed server-save choice stages verified bytes as `selected.sav` beside the ROM's slots and writes `selection.json` before uploading them as a new head on RomM. The intent holds the destination, raw file hash, RomM content hash and prior local hash. Before writing the new head, the previous destination head is verified and kept as an unslotted archive on RomM, outside its slot retention cap. Its download stays beside staging as `previous-head.sav`. Slot replacement and ledger writes finish before the intent is cleared. A restart inspects the destination head before ordinary sync: matching staged content completes locally, while a later head or new local progress cancels the unfinished local replacement without replaying an overwrite. Staged bytes remain as an extra copy. Pending intents are retried on reconnect even when no slot is unsynced. A durable player fresh-load marker is saved at the commit boundary, after strict sync, download verification and preservation of the previous head. A definitive refusal restores its previous value; an uncertain upload retains it for recovery, so a paused emulator cannot resume over selected bytes after a crash. Player files use the existing backup, read-back and torn-placement rules.

RomM also keeps a server-scoped catalog under `files/romm/servers/<server key>/catalog.json`. At startup it publishes saved titles, platform metadata, artwork addresses, and complete platform listings before waiting for the server, then refreshes the running shell in place. The early snapshot adds to any games already in memory, preserves missing games' placements until a complete listing reports, and cannot release restored source holds or start pending save sync; connection checks still gate sync. Its download badges use verified markers and file sizes without reading ROM bytes, so downloaded games do not delay that connection; live listings still check their hashes. A refresh updates metadata in memory per page and durably flushes one snapshot at completion or cancellation, skipping unchanged data. Searches and interrupted pagination retain the last complete listing. Network recovery reconnects and ingests the refreshed catalog in the running shell. Authentication failures still require sign-in; an unavailable server can use its saved catalog. Verified downloaded ROMs can launch without a network request.

RomM image bytes use a bounded cache under that server's ROM cache root. Cache hits still require a credential-free address on the configured origin. Both screens share image requests, and temporary files keep unfinished images out of the cache. Android may evict ROMs and artwork from cache storage; the catalog is kept separately so their metadata survives that eviction. The chosen home loop is decoded once to a WAV file under `cache/home-music` and played from there, so playing it needs no decoder; only the current track's copy is kept, and an evicted copy is decoded again the next time music starts.

RomM and SteamGridDB credentials use the existing encrypted DataStore, with encryption keys in Android Keystore. Setup backups never carry either secret.

Local media uses the same picked library trees, including separate ES-DE folders. Images and gamelists stay in those trees; the media/facts index and the art-and-info source label are rebuilt in memory after a granted scan. The existing Game art choice is portable; local media works even when public Game art is off. RomM summaries and facts extend its existing server catalog, which stays device-owned with the other caches.

APK plugin consent and the per-plugin Moonlight routing choice use host-owned `apk_plugins.xml` preferences, separate from `foldcade.xml`. Each key binds the package, sorted current signer SHA-256 set, and scope. Consent commits before the switch is published. Revocation applies on the next broker call; full package removal drops its entries, including while Home is stopped. Android cloud backup and device transfer include only `foldcade.xml`, so this preferences file never travels, and the setup backup exporter never reads it. A signer change has no matching grant. Downloaded APKs are temporary files under `cache/apk-plugins`, removed after verification or session staging; install state is transient.

`moonlight_addresses` in `SessionStore` keeps each computer's last reached LAN address, HTTPS port and optional MAC for cold broker calls. It is classified DeviceOnly beside the existing pairings. Before this record exists, a paired computer must be located once before the broker can report its address. Pairings still require the same keystore identity fingerprint.

## Backup and restore

Settings › System › Backup keeps Home, collections, hidden games, settings, chosen art, added themes and play history in one zip, wherever the player picks. Restore previews what it replaces and what is missing here. Play history only adds; importing the same backup twice adds nothing. Games, saves, sign-ins, pairing keys and Android permissions do not travel.

`foldcade-backup.json` names format 1, the creation time in epoch milliseconds, app version, device and summary. `settings.json` holds typed, allowlisted preferences; `home.txt` and `same-games.txt` keep their existing encodings; `art-choices.json`, `play-history.zip` and `themes/<file>.zip` keep art choices, the existing play-history transport and added packs. Reading bounds entries and total inflation, including skipped entries, rejects traversal and duplicate names, and refuses a missing marker or newer format. The format-1 test fixture must keep reading. Packs go through Add a theme's validator and start a fresh trial; an explicit restore can bring an older release back. An invalid pack is skipped, with the usual theme fallback. Export streams archives one at a time, skips packs that do not fit the combined 128 MiB cap, and names the omitted count in its done line. Imports keep large sections in private files; metadata and decoded play records also have memory budgets.

`BackupSettings.keys` is the classification table. Portable choices replace the corresponding preferences, including clearing absent keys. A backup without a RomM address keeps this device's current connection; one naming a different address says so in the confirmation detail. Onboarding, grants, save marks and pending returns, player and firmware state, cached catalogs, GameStream identity and pairings, and retired migration keys stay device-owned. No plugin keeps another app-owned settings file. RomM's device registration, save ledgers, conflicts and staged saves, GameNative's cached catalog, the artwork index, caches and theme rollback records stay here. A RomM address carrying userinfo, a query or a fragment is dropped. A different restored address requires sign-in before this device's existing token can be used there; the secret itself stays put.

Emulator choices (`system_player:` per system, `game_player:` per game tile) travel as strings with the Home board whose tile ids they name. A restored choice whose emulator is not installed here waits, as on its own device: the game opens with the next choice and says so.

`screen_layout` and `play_on` travel as strings; `primary_top` keeps the Thor's physical display role. A backup predating Layout and Play on clears those choices so startup uses the defaults or the older Main screen migration. Backup dialogs stay with their Settings page and follow the session off a dark or occupied screen. System contracts row padding with the shared menu fit, keeping its eight rows visible when both Android prompts are pending.

Library folders travel as URI/name records. Restore keeps this device's current library trees first, then adds the backup's trees for which this install has a persisted read grant. It names missing grants to pick again, including media-only trees. Re-picking the same tree restores the same ids and makes its local media available again. Device-owned `restore_holds` preserves missing games' places, hiding and collection membership across restarts; their tiles draw as empty slots. Only complete folder scans release the trees they reached, including an unchanged empty scan after a card returns; an incomplete forest cannot settle the library. RomM releases after a complete live catalog; an older offline cache can fill Home without releasing missing restored games. Moonlight publishes its catalog before releasing holds per computer after its paired app list reports, including a valid empty list. GameNative and DroidDeck wait for installation, a successful shortcut read, completed folder scanning and outstanding backed-up folders. Both refresh when the last outstanding folder reports. GameNative also requires games or an existing catalog; an empty first read does not manufacture one. Android apps use the ordinary installed-app merge. `restore_folders` keeps outstanding picks through another backup. Settings › Library shows those folders by name with the existing Attention badge. Their page opens on Pick again, which starts the ordinary folder picker at the saved tree where Android accepts it; Remove stays in a second row. Picking a different tree adds it without forgetting the pending source or its places. Remove forgets a pick, including one from an old card. A held gap's Y heading names its known folder, RomM or computer as Waiting for that source; an unknown source keeps Empty slot. X removes a held gap from every place and its hold, using the ordinary Remove verb and Undo; Folders and All never act on a root gap. Explicitly removing a folder, RomM connection or computer releases that source's holds.

Restore first stages the picked archive's original bytes, then writes the current setup to a temporary `files/backup/before-restore.zip` and renames it durably. A ready marker lets startup finish an interrupted rename; stopping earlier leaves the old undo copy intact. A preparation failure before readiness removes the unfinished stage so another try can proceed. This before-copy leaves out resource-pack archives: restores keep installed packs. Undo takes the same path, so it toggles the saved choices without duplicating large packs. An optional `redoRestore` flag inside the before-copy's format-1 manifest names the next action: Undo after a restore, Redo after an undo, then Undo again. It is tied to the archive's atomic rename, needs no separate preferences or sidecar, and is absent from ordinary exports. Old before-copies default to Undo. The bounded header reader names the button without decoding play history or themes; confirmation still uses the full validating reader. Undo and Redo name what they put back, with the before-copy's date; play history from both stays. Nothing else deletes the before-copy. After handling a staged restore, every startup removes abandoned import, apply and export workspaces and temporary files, and keeps only the newest failed archive. A ready restore's recovery inputs stay until it finishes.

The next process applies the stage before SessionStore or ShellController exists. File changes and the remaining-steps notice land first, then portable preferences, holds and a commit marker commit together. A stop after commit only finishes cleanup. A small attempt file also counts processes stopped during application. Ordinary I/O failures get one retry during startup. After two failed attempts, Foldcade keeps the failed archive aside, restores the original portable preferences and chosen art, and starts normally with one failure line. It never clears app data or restores save marks. If it cannot record an attempt, it abandons that apply safely rather than starting an uncounted retry. Restored lists the remaining steps, naming Settings › Library for missing folders and offering a focused Library shortcut with OK as the safe button. With no steps it says All set. Pairing status comes from this device's stored pairing and identity, even before Moonlight finishes loading; the pairing step is offered only when the backup carried computers, not for an unrelated unpaired computer discovered here.

Android's own backup stays off (`allowBackup=false`); the manifest and backup rules are unchanged. One preferences file mixes safe settings with device-bound save-sync state and grants. Auto Backup is file-granular, runs out of the player's sight and needs a Google account. Silently restoring a save mark could call an unsynced save synced. Explicit backup carries the choices that can safely travel and leaves save reconciliation on this device alone.

## Verification

`SettingsPersistenceTest` recreates stores/controllers after settings changes and covers startup catalog timing, folder edits, saved sources, shelf choices, controller mappings, shared folder references, unavailable themes/tracks, and invalid values. `HomePersistenceTest` covers version 1 migration, unusual identifiers, browsing choices, pending moves, malformed records, and renamed folders during startup. `PlaySessionBackupTest` parses each backup mode and checks settings/file inclusion and credential exclusion. `PlayMoveTest` (host) covers moves, undo, reloads, merging an export, and refusing foreign zips; `PlayHistoryTest` covers moved play feeding a tile's totals and schedule, folded copies, and an export carried to another device. `SetupArchiveTest`, `SetupBackupTest`, `SetupReviewRegressionTest` and `BackupTest` cover the setup format, typed values, classification guard, inflation bounds, preview counts, crash replay, undo, credential origin binding and restore holds through catalog merges.

Run all unit tests and API 33 checks with:

```sh
./gradlew testDebugUnitTest :plugins:moonlight:test --configuration-cache
```

These tests cover application save/restore logic and file round trips. Preference tests use an in-memory Android interface implementation; they do not simulate an interrupted Android disk write. Physical-device force-stop/relaunch, power-loss, and device-transfer checks remain separate validation steps.

Collection ids use a saved high-water counter and are never reused after removal. Deleting a collection also drops hidden membership references to it. Older layouts infer the counter from surviving ids and recovery records.

Undo keeps the before/after delta of the most recent removal in memory for eight seconds. It applies that inverse to the current board, preserving catalog arrivals and their positions. Any later saved user edit clears undo; library merges do not. The current catalog is reapplied after Undo so games that no longer exist are not resurrected. Undo is never saved across restarts.
