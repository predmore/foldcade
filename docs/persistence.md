# Persistence audit

Settings and confirmed Home edits are restored from the app-private `foldcade` shared preferences. `SessionStore` owns those keys, and `ShellController.publish` saves changes made through controller input or the settings screen. Preferences use Android's asynchronous `apply`; save reconciliation markers and pending returns use `commit` before handing control to a player. Android flushes pending preference writes during component lifecycle transitions ([SharedPreferences documentation](https://developer.android.com/reference/android/content/SharedPreferences)).

## Saved choices

- Personalization: theme name, whether the background was explicitly selected, background motion, motion speed, and controller confirmation/dismissal choices per device.
- Sound: music enabled, volume, and track id. Theme and track selections fall back when unavailable without overwriting the saved choice during startup. Nonfinite volume values fall back to the default.
- Library: source folder URIs, RomM origin, All's order (A–Z or Recent), automatic placement of new games, and the artwork switch.
- Home: tile positions and empty slots, collections (folders the user made in older releases become collections, and the built-in Favorites of older releases becomes an ordinary one, or goes if it was empty and never renamed), confirmed names and icons, each folder's and collection's sort (in a row of its own, so an older release keeps the arrangement, which a sort never changes), hidden tiles and their former root/group slots, removed system folders with their root slots and games still filed in them, and when Recently played may first appear.
- Apps: installed apps are filed on the Home board like any game, in Android Games, Android Apps, or Emulators, and hidden there. Releases with separate Android shelves saved their own overrides; the first launch after them hides the apps hidden on a shelf on Home and forgets the rest.
- Players: save folder URIs and whether detection found them, save hashes, and pending save returns. Playing without syncing applies to one launch and is never saved. Old skipped save-folder and hosted-save offers are removed on startup.
- Same games: `same_games` maps each copy of a game several libraries have (same system and file name) to the one tile it is shown as. It is kept when a copy goes away, so the tile keeps its id while a server is offline or removed. The Home board and art choices move onto the tile when it forms; play history stays under each copy's id and is read through the tile.
- Onboarding: Home, library-folder, usage-access, and controller prompt answers.

Brightness, the Home role, notification access, usage access, and optional all-files access belong to Android. The shell reads their current state rather than restoring an app-owned copy. SAF folder URIs are saved after acquiring persistable access. Removing or replacing one folder reference keeps its grant while another saved source or player still uses that tree, including save folders named by documents inside it. Detection clears a found folder when its writable reach or required player grant goes away, or another reachable copy makes it ambiguous, and searches again, so missing-sync notices return. User-picked folders stay chosen; a missing grant unbinds them until access returns.

Settings › Emulators › Find saves opens Android's all-files access page only on request. With access, detection can use Foldcade's private shared-storage provider after real SAF grants. Its document URIs use the same save reconciliation marks as SAF folders. Home resume re-reads access and detection; revocation clears found provider folders and tries SAF again. No saved switch can hide missing-sync notices, and explicit folder picks are never replaced. Android/data and Android/obb still need their own SAF grants.

## Home snapshots and startup

The Home format is versioned. Version 2 encodes each field separately as Base64url, so opaque game ids or names containing record separators cannot damage neighboring fields. Version 1 layouts still load and are upgraded on the next saved snapshot. Invalid version 2 records are skipped individually. Set and folder ordering is deterministic, and saving an unchanged snapshot skips the preference write.

A lifted tile is serialized at its last confirmed position. Confirming a move saves the new position; canceling or restarting during an unfinished move restores the original position. Open dialogs, rename drafts, editing state, and active external-app sessions are transient.

Saved Android, GameNative, Moonlight, DroidDeck, and library placements are retained while their respective catalogs load. An empty startup catalog does not establish that a game was removed, so a folder whose games are still loading keeps its place and its name. A reported catalog can then remove games that are actually gone.

No games, no folder. A folder Foldcade makes, for a platform or for Android, GameNative, Moonlight, or DroidDeck, appears with its first game. Filing a game into a collection never empties its folder. Hiding every game in an automatic folder removes that folder from the grid. A folder the user removed stays off Home until Show in Hidden. A new game brings back only a folder that disappeared because it emptied. Pinning a game files it into a removed folder without bringing that folder back. Folders hold games, not the apps that run them: an installed app a player plugin covers, such as Azahar, Dolphin, GameNative, Moonlight, or DroidDeck, goes in its own Emulators folder, under the same rule. Releases before the Emulators folder filed those apps under Android Games or Android Apps; each moves to Emulators once, and after that stays wherever the user puts it. User-made groups are collections, which stay, even empty, until the user removes them, which deletes them.

## Files, secrets, and transfer

Confirmed GameNative catalogs use the existing durable-file writer: write a temporary sibling, sync its bytes, replace the destination, and attempt to sync the parent directory. Play history is appended and synced under `files/play-sessions`, with each game's name at launch in `names.log` beside `events.log`, so Play activity still names a game that has left every catalog. A session removed from Play activity is one more `Removed` line, never a rewrite; readers leave that session out. RomM's durable device/save data and replaced player-save backups remain under `filesDir`, as does `save-handover`, where a save kept as folders waits as a zip until its library has kept it; downloaded games and regenerable artwork bytes use cache storage.

Resource packs Foldcade did not ship live in `files/themes`. `files/theme-installs.json` records each archive, the updates kept beside them in `files/themes-previous`, and the [trials](themes.md#releases-and-trials) that put a crashing pack back. It is written with the durable-file writer. A restored backup puts every pack on trial once, since restored archives have new modification times.

A confirmed server-save choice stages verified bytes as `selected.sav` beside the ROM's slots and writes `selection.json` before uploading them as a new head on RomM. The intent holds the destination, raw file hash, RomM content hash and prior local hash. Before writing the new head, the previous destination head is verified and kept as an unslotted archive on RomM, outside its slot retention cap. Its download stays beside staging as `previous-head.sav`. Slot replacement and ledger writes finish before the intent is cleared. A restart inspects the destination head before ordinary sync: matching staged content completes locally, while a later head or new local progress cancels the unfinished local replacement without replaying an overwrite. Staged bytes remain as an extra copy. Pending intents are retried on reconnect even when no slot is unsynced. A durable player fresh-load marker is saved at the commit boundary, after strict sync, download verification and preservation of the previous head. A definitive refusal restores its previous value; an uncertain upload retains it for recovery, so a paused emulator cannot resume over selected bytes after a crash. Player files use the existing backup, read-back and torn-placement rules.

RomM also keeps a server-scoped catalog under `files/romm/servers/<server key>/catalog.json`. It restores titles, platform metadata, artwork addresses, and complete platform listings after a cold offline start. Searches and interrupted pagination retain the last complete listing. Network recovery reconnects and ingests the refreshed catalog in the running shell. Authentication failures still require sign-in; an unavailable server can use its saved catalog. Verified downloaded ROMs can launch without a network request.

RomM image bytes use a bounded cache under that server's ROM cache root. Cache hits still require a credential-free address on the configured origin. Both screens share image requests, and temporary files keep unfinished images out of the cache. Android may evict ROMs and artwork from cache storage; the catalog is kept separately so their metadata survives that eviction. The chosen home loop is decoded once to a WAV file under `cache/home-music` and played from there, so playing it needs no decoder; only the current track's copy is kept, and an evicted copy is decoded again the next time music starts.

RomM and SteamGridDB credentials use the existing encrypted DataStore, with encryption keys in Android Keystore. The backup rules include `sharedpref/foldcade.xml` and ordinary files, and exclude the credential DataStore directory. The manifest's existing `allowBackup=false` policy still disables cloud backup. Device transfer behavior with that flag depends on the device; the transfer rules now include saved settings and Home edits ([Android backup documentation](https://developer.android.com/identity/data/autobackup)). Credentials must be entered again, and provider-specific folder grants may need to be reacquired on another device.

## Verification

`SettingsPersistenceTest` recreates stores/controllers after settings changes and covers startup catalog timing, folder edits, saved sources, shelf choices, controller mappings, shared folder references, unavailable themes/tracks, and invalid values. `HomePersistenceTest` covers version 1 migration, unusual identifiers, browsing choices, pending moves, malformed records, and renamed folders during startup. `PlaySessionBackupTest` parses each backup mode and checks settings/file inclusion and credential exclusion.

Run all unit tests and API 33 checks with:

```sh
./gradlew testDebugUnitTest :plugins:moonlight:test --configuration-cache
```

These tests cover application save/restore logic and file round trips. Preference tests use an in-memory Android interface implementation; they do not simulate an interrupted Android disk write. Physical-device force-stop/relaunch, power-loss, and device-transfer checks remain separate validation steps.

Collection ids use a saved high-water counter and are never reused after removal. Deleting a collection also drops hidden membership references to it. Older layouts infer the counter from surviving ids and recovery records.

Undo keeps the before/after delta of the most recent removal in memory for eight seconds. It applies that inverse to the current board, preserving catalog arrivals and their positions. Any later saved user edit clears undo; library merges do not. The current catalog is reapplied after Undo so games that no longer exist are not resurrected. Undo is never saved across restarts.
